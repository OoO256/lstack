# rebase-note — 배포 노트

배포에 실린 PR 을 사내 슬랙 공지 한 편으로 옮긴다. 독자는 이 코드를 안 본 팀원이다.

## 1. 범위 뽑기

```bash
git fetch origin
LATEST=$(git tag -l 'v*' --sort=-version:refname | head -1)
git log --oneline "$LATEST"..origin/main
```

- 직전 태그부터가 기본 범위다.
- **공지가 안 나간 이전 릴리스가 있는지 확인한다** — 태그는 올랐는데 슬랙 공지가 없으면
  그 범위도 후보다. 넣을지는 사용자에게 **묻는다**.

## 2. 초안에는 PR 을 전부 넣는다

**빼는 것은 사용자의 권한이다. 모델은 임의로 생략하지 않는다.**
지운 항목은 사용자가 지웠다는 것을 알지만, 애초에 안 쓴 항목은 있었는지조차 모른다.

- 범위에 든 PR 은 **하나도 빠뜨리지 않고** 한 줄씩 쓴다.
- 판단이 서지 않는 항목도 쓴다. 지울지는 사용자가 정한다.

대신 **지우기 쉽게 배치한다** — 잘릴 가능성이 큰 항목을 뒤쪽 섹션에 모은다. 팀원이
쓰게 될 것 · 물어볼 것 · 판단에 영향 주는 것이 앞이고, 나머지가 뒤다. 실제로 자주
잘리는 것은 이런 항목이다:

- 내부 계측·비용 정합성 수정 — 원장 누락, 유입 태깅 오차 같은 것. 고쳐졌다는 사실이
  팀원의 행동을 바꾸지 않는다.
- 리팩터링 · 하니스 · 테스트

한 섹션이 통째로 잘릴 것 같으면 그 섹션으로 묶어두면 된다. 판단 근거는 채팅에 한 줄로
덧붙이고, 노트 본문에는 넣지 않는다.

## 3. 어떻게 쓰는가

- **PR 제목을 그대로 옮기지 않는다.** 사용자에게 보이는 결과로 다시 쓴다.
  내부 어휘(슬롯, 원장, 티어, 게이트)는 팀원 어휘로 바꾼다.
- **제목만으로 이해되면 설명을 붙이지 않는다.** 설명 없는 한 줄이 정상이다.
- 설명을 붙일 때는 **한 줄**. 배경·원인·타임라인·재현 경위는 PR 이 갖는다.
- **숫자는 그 숫자가 없으면 뜻이 안 통할 때만.** "1,000행에서 잘려 최근 53개만
  보이고 있었다"는 남긴다(신뢰도 문제). "실패 37건 중 22건", "23%" 류의 근거 수치는
  대부분 뺀다.
- **행동이 필요한 항목엔 방법을 한 줄로 붙인다** — "저에게 설치 파일을 받아서 플러그인
  설치 후 회사 구글 계정으로 인증합니다".
- 채널·탭·버튼은 **팀원이 아는 실제 이름**으로 부른다 (`#reflica_feedback`, `내 목소리 탭`).
- 문체는 짧은 존댓말. 한 항목 두 줄을 넘기지 않는다.

## 4. 형식

```
<서비스> v<버전> 배포

<섹션 이름>
<한 줄 제목> (#PR) — <필요하면 한 줄 설명> <필요하면 cc>
...
```

- 섹션은 고정 목록이 아니다. **그 배포의 내용에 맞춰** 독자군으로 나눈다
  (사용자 기능 / 기획·분석 / 개발, 또는 영상 실패 줄이기 / 어드민·계측).
- 마커(`-`, `•`)는 있어도 없어도 된다. 한 노트 안에서만 일관되면 된다.
- 최종 출력은 **그대로 복사 가능한 한 덩어리**로 준다. 설명은 블록 밖에.

## 5. cc

cc 는 그 항목을 **제보·요청한 사람**이나 **후속을 이어받을 사람**에게 붙인다.
확신이 없으면 **비워두고 사용자에게 묻는다** — 틀린 cc 는 안 붙인 것보다 나쁘다.

## 6. 아직 안 켜진 기능

배포는 됐지만 운영 토글·링크 배포가 남은 항목은 공지에 넣기 전에 사용자에게 알린다.
공지를 보고 팀원이 써 보려다 안 되면 그 자리에서 신뢰가 깎인다.

# 예문

실제로 사내 슬랙에 나간 공지 두 편. 둘 다 사용자가 직접 쓰거나 손본 최종본이다.
원칙보다 이쪽이 빠르다. (실명은 가명으로 바꿨다.)

## 예문 1 — reflica v0.3.19

```
reflica v0.3.19 배포

사용자 기능
• 내 목소리 사용하기 (#422) (cc @홍길동)
    ◦ 아직은 워크플로우에 소극적으로 적용했어요. "내 목소리 사용해줘"라고 대화 중 agent에게 요구하면 목소리를 사용할 수 있어요. 목소리 등록은 홈 화면의 <내목소리 탭>과 대화 도중 agent의 <내 목소리 사용하기> 선택지를 클릭하면 나오는 모달 모두에서 가능해요

영상 실패 줄이기 (내보내기 실패의 주원인들) (cc @김철수)
- 에이전트가 턴을 끝내기 전에 자기 에러를 고친다 (#402) — 깨진 씬 코드로 응답을 끝내지 못하게 막는 검사 지점 추가. 최근 2주 내보내기 실패 37건 중 22건이 이 부류였다.
- 렌더 없이 정적으로 런타임 에러 잡기 (#459) — render still 로 랜더링을 하지 않아도, eslint getStaticValue 를 사용하면 상수 변수의 값을 검사할 수 있음을 발견해서 적용했어요
- 씬 URL 의 UUID 오타 차단 (#458) — 에이전트가 36자 UUID를 손으로 옮겨 적다 틀려 내보내기가 통째로 실패한 사례 2건. 완료 경계에서 검사.
- 장면 그림 누락을 그 자리에서 드러낸다 (#401) — 씬 코드가 참조하는 이미지가 아예 안 만들어졌는데 아무 신호도 없던 문제(위임 번호 한 칸 밀림).

어드민·계측
- 영상 피드 탭 (#460) — 통계/영상 피드 탭에서 사용자가 만든 영상과 대화를 시간 역순으로 볼 수 있어요.
- 대화 날짜 구분선 + 프로젝트 생성순 정렬 (#456) — 며칠에 걸친 대화에서 언제 얘기인지 보이게. (cc @이영희)
- 프리뷰 멈춤 시간 측정 (#455) — "재생이 안 된다"는 불만을 분포로 파악하기 위한 계측만. 성능 개선은 아직 없음.
```

읽을 점

- 섹션 이름이 카테고리가 아니라 **묶음의 목적**이다 — "영상 실패 줄이기 (내보내기 실패의 주원인들)".
- 계측만 하고 개선은 없는 항목은 **그렇다고 적는다** ("성능 개선은 아직 없음").

```
저장소 한도 초과를 푼 경위 기록 (#482) — Storage 가 Pro 한도 100GB 의 120GB 까지 찼던 건의 정리 근거. 코드 변경 없음.
```

## 초안 → 최종본에서 무엇이 잘렸나

예문 2 는 모델이 쓴 초안을 사용자가 손본 것이다. 잘린 것이 곧 원칙이다.
**삭제는 사용자가 했다** — 초안에는 아래 항목이 전부 들어 있었고, 그래서 사용자가
지울 수 있었다.

| 초안 | 최종본 | 왜 |

| 계측·비용 섹션 3건 (fal 비용 원장 #467, 광고 유입 #477·#483) | **통째로 삭제** | 고쳐진 사실이 팀원의 행동을 바꾸지 않는다 |
| "목소리 만들기 실패 이유를 알려줍니다 — 배포 첫날 3연속 실패하고 떠났어요. 실제 원인(6.7초, 최소 10초)을…" | "목소리 만들기 실패 이유를 표기 (#470)" | 제목만으로 통하면 설명을 안 붙인다 |

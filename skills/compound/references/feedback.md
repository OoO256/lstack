# 피드백을 기록하고 다음 작업에서 사용한다

compound는 교정의 정리·개선 제안을, start와 reviewer는 승인된 기준의 재사용을 위해 읽는다.
기록은 다음 작업의 판단을 바꿀 만큼만 남긴다. 대화 원문 전체나 전역 점수판을 축적하지 않는다.

## 근거와 적용 범위를 함께 남긴다

기존 handoff의 `결과`에 실제 교정과 결론을, `한계와 후속`에 미해결 이해부채·개선 후보를 둔다.
handoff 작성 전 해당 스킬을 읽는다. 같은 원인의 기록은 최신 결론으로 합치며 새 장부를 만들지 않는다.

한 교정에는 필요한 만큼 아래 내용을 짧게 묶는다:

- 위치·사례: 코드 경로와 함수, 필요하면 당시 커밋. 예상한 동작과 실제 차이.
- 사용자 근거: 짧은 발언 또는 승인한 코드 사례. 비밀·개인정보·무관한 대화는 옮기지 않는다.
- 원인·범위: 어느 책임에서 왜 읽기 어려웠는지, 어디까지 적용하고 무엇은 예외인지.
- 결론: 이번 작업의 요구인지, 향후에도 적용하라고 명시한 기준인지, AI가 추론한 제안인지 구분.
  적용된 수정·기준의 위치와 남은 문제를 연결한다. 실제 코드 이해를 확인하지 않았다면 그 한계도 적는다.

예: “외부 요청 필드 검사가 긴 조건식에 묻혀 검증 대상을 알기 어려웠다”는
“함수는 짧아야 한다”가 아니라 “입력 경계의 복잡한 구조 검증은 스키마로 드러낸다”는 후보가 된다.
단순 내부 분기는 예외다. 이 설명 예제를 실제 사용자가 승인한 코드 사례로 기록하지 않는다.

## 승인된 기준의 소유 위치

| 내용 | 유지할 위치 |
|---|---|
| 프로젝트에 관계없는 작성 방식 | lstack의 start 작성 원칙과 관련 담당 스킬 |
| 프로젝트의 분류·용어·인터페이스·대표 코드 | 해당 책임의 기존 문서·작성 지침 |
| 교정 근거·미해결 지점·승인 전 제안 | 현재 작업의 handoff |

규칙을 옮길 때는 복제하지 않고 원본 위치를 연결한다. 사용자 승인 사례는 경로·심볼과 필요한
커밋을 남기고, 왜 적합했는지와 적용 범위를 적는다. 코드 전문을 문서에 복제하지 않는다.
적절한 프로젝트 문서가 없으면 위치를 제안한다. 임의로 전역 설정·메모리 파일·새 정책 문서를 만들지 않는다.
ARCHITECTURE는 책임과 참조 위치만 안내하며 피드백 목록·작성 매뉴얼을 소유하지 않는다.

## 다음 작업의 조회

1. 프로젝트의 적용 지침(AGENTS.md·CLAUDE.md 등)과 그 지침이 연결한 담당 문서·승인 사례를 읽는다.
2. 현재 작업의 경로·책임·용어로 기존 `docs/worklogs/`의 관련 handoff를 검색한다.
   원본 위치가 확인되면 그 원본을 읽는다. 관련 기록이 없으면 넘어가며 과거 모든 세션을 수집하지 않는다.
3. 현재 코드·소비자와 대조해 여전히 적용되는 기준만 선택한다. 한 작업의 선호를 전체 프로젝트
   규칙으로 확대하지 않는다. AI의 제안·추정 점수·옛 구현자의 정당화는 승인된 기준이 아니다.
4. 승인된 범위 안에서는 바로 재사용한다. 지금의 사용자 요구와 충돌하면 현재 명시 지시를 따르고,
   남은 모순만 질문한다. 근거가 사라졌거나 의미가 바뀐 사례는 미확인으로 표시한다.

선택한 기준·사례의 경로를 구현자와 독립 리뷰어에게 동일하게 전달하되, 구현자의 해설은 분리한다.
전체 피드백 목록을 매번 컨텍스트나 사용자 보고에 붙이지 않는다.

## 이해부채와 효과 확인

설명 없이는 판단이 막힌 위치만 남긴다. 도메인 지식의 빈틈이면 설명, 이름·경계 문제면 작은 정리,
실패 전파가 숨었으면 계약·제어 흐름 개선으로 구분한다. 이번 실행 경로에 필요한 정리만 승인받고,
나머지는 다음 관련 변경 때 다시 본다. 코드 전체를 전수 조사하거나 점수로 리팩토링을 강제하지 않는다.

실제 코드에서 사용자가 동작·수정 위치를 예상하고 버그 원인을 좁힐 수 있었는지와 같은 교정의
재발을 본다. 시간이 관찰된 경우에만 이전 작업과 비교한다. 재발 없음은 해당 사례에만 유효하며,
기록이 없거나 적용 기회가 없었다면 개선을 검증했다고 하지 않는다.

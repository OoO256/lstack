# 코드 작성 원칙

`start`에서 설계·구현할 때 읽는다. 구조를 어떻게 조사하고 합의할지는 `start`와 `align`이,
사용자가 요청한 독립 검토는 `reviewer`와 각 reviewer가 담당한다.

## 이름과 타입

- 일반 변수는 설명적인 명사, boolean은 의문문, 함수·메서드·이름 있는 화살표 함수는
  동사로 시작한다. 접두사만 맞추지 말고 이름으로 대상·역할·동작·부작용을 예상할 수 있게 한다.
- `isAdmin`은 여부 반환, `requireAdmin`은 권한 없으면 거부, `grantAdmin`은 권한 부여다.
  역할이 다르면 이름도 구분한다. 이유·제약을 설명하는 주석까지 없애지는 않는다.
- `as const` 외 캐스팅은 테스트·mock 포함 금지한다. 타입과 데이터 경계 자체를 고친다.
- 새 이름은 기존 계약·소비자·개명 전 이름·SDK 공식명과 비교한다. 같은 역할에는 같은
  어휘를 쓴다. `Policy`·`Manager` 같은 단어 자체나 새 이름 수로 옳고 그름을 판단하지 않는다.

## 책임과 데이터

- 공유 위치는 실제 소유자·소비자·의존 방향으로 정한다. 공통 책임·생명주기는 모을 수 있다.
  `BaseAgent`의 공통 생명주기나 사용자가 선택한 `EventValidationPolicy`를 불필요한 추상화로
  일반화하지 않는다. 모든 개념을 별도 파일과 1:1로 쪼개지도 않는다.
- 원본에서 계산되는 불필요한 파생값, 단일 필드 포장, 통과만 하는 계층을 추가하지 않는다.
  스키마·enum·리터럴 규칙은 기존 원본을 재사용한다. 사용처 수·줄 수는 조사 단서이지 판정 기준이 아니다.
- lint가 검사하는 문법 규칙과 실제 코드·소비자·부작용을 읽어야 하는 의미 판단을 구분한다.
  이 작성 원칙이 프로젝트에 lint 규칙을 설치하거나 검사·리뷰를 자동 실행하라는 뜻은 아니다.

## 테스트

테스트를 쓰거나 바꿀 때는 [행동 테스트 판별 기준](../../pr/change-detector-tests.md)을 읽는다.
실제 사용자 관찰 동작과 오류 경로를 검증하고, 깨졌을 때 버그인지 판단할 수 있는 테스트를 쓴다.

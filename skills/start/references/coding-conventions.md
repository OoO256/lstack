# 코드 작성 원칙

설계·구현 전에 읽는다. 프로젝트의 해당 책임 지침과 사용자 승인 코드 사례가 있으면 함께 읽고,
현재 코드라는 이유만으로 좋은 사례로 간주하지 않는다. 이 문서는 lint 설치나 리뷰 자동 실행 지시가 아니다.

## 분류와 책임

- 사용자와 합의한 추상화 계층을 따른다. 같은 계층에서는 같은 종류의 책임을 다루며, 상위 코드는
  작업의 순서를, 하위 코드는 각 작업의 방법을 드러낸다. 폴더는 책임·변경 이유를 반영한다.
- 종류·소유·호출을 구분한다. 모양을 맞추려고 다른 역할을 같은 인터페이스로 강제하지 않는다.
  같은 계약의 구현체는 입력·반환·실패 의미를 일관되게 하되, 실제 차이를 숨기지 않는다.
- 상태·규칙·스키마의 원본과 소유자를 명확히 한다. 불필요한 파생값·통과 계층은 추가하지 않는다.
  실제 공통 책임·생명주기는 추상화할 수 있다. 모든 개념을 별도 파일로 나누거나 사용처 수로 판단하지 않는다.

## 이름과 타입

- 일반 변수는 설명적인 명사, boolean은 의문문, 함수는 동사로 시작한다. 대상·역할·동작이
  필요충분하게 드러나야 한다. 접두사만 맞추거나 모든 구현 상세를 이름에 나열하지 않는다.
- `isUserAdmin`은 여부, `requireUserAdmin`은 권한 없으면 거부, `grantUserAdmin`은 권한 부여다.
  이름·입력·반환으로 예상한 동작과 실제 부작용을 대조한다. 역할이 다르면 이름도 달라야 한다.
- 같은 역할은 기존 계약·사용자의 어휘를 재사용한다. 이름이 길어지면 여러 책임이 섞였는지도 본다.
  이름이 설명할 동작과 주석이 설명할 이유·제약은 구분한다.
- `as const` 외 타입 캐스팅은 테스트·mock에도 금지한다. 우회 단언 대신 타입·입력 경계를 고친다.

## 문단처럼 읽히는 함수

함수의 상위 흐름을 읽다가 저수준 처리의 해석에 오래 머물면, 그 의미 단위를 구체적인 동사 이름의
함수로 추출한다. 예를 들어 요청 처리에서 입력 필드 검사식이 본문 대부분을 차지하면 입력 검증을
분리한다. 호출부에서 하위 함수 여러 개의 내부를 동시에 기억해야 하면 경계와 계약을 다시 본다.
줄 수를 기준으로 자르거나 자명한 표현까지 함수로 감싸 탐색을 늘리지 않는다.

## 검증과 기존 라이브러리

- 복잡한 외부 입력 구조를 긴 `typeof`·조건식 조합으로 직접 검사하기 전에 기존 스키마를 찾는다.
  Zod를 사용한다면 스키마를 원본으로 타입을 유도하고 `safeParse`의 성공 데이터·실패를 처리한다.
  이미 검증된 내부 데이터나 단순 분기까지 다시 스키마로 검사하지 않는다.
- 범용 기능은 기존 프로젝트 구현 → 표준 API → 적합한 라이브러리 순으로 확인한다.
  동시 실행 제한에는 `p-limit`, 컬렉션 처리에는 기존 lodash 사용 등을 검토한다.
  의존성을 무조건 추가하지 말고 지원 환경·유지보수·요구 동작을 비교한다. 동시성 제한과 취소·재시도는 별개다.
- 직접 구현이 필요하면 기존 기능이 충족하지 못하는 요구를 짧게 설명한다.

## 테스트와 참고

동작 변경은 가능한 경우 실패하는 행동 테스트부터 작성하고 필요한 최소 테스트로 검증한다.
[행동 테스트 판별 기준](../../pr/change-detector-tests.md)에 따라 오류·공개 계약을 확인한다.
기존 테스트 삭제는 별도 승인 없이 하지 않는다. 문구·파일 배치만 잠그는 테스트를 추가하지 않는다.

판단이 애매할 때 [Frontend Fundamentals](https://frontend-fundamentals.com/code-quality/code/)의
가독성·예측 가능성·응집도·결합도와 [Extract Function](https://refactoring.com/catalog/extractFunction.html)을 참고한다.
원칙을 기계적으로 적용하지 말고 실제 사용자 승인 사례와 소비자로 판단한다.

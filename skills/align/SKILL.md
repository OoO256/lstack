# align — 구조를 이해하고 구현 범위를 합의한다

사용자가 코드를 열었을 때 주석 없이도 각 부분의 역할과 동작을 예상하고,
나중에 버그가 나도 증상에서 원인과 확인할 코드를 따라갈 수 있게 한다.
계획을 보여준 것, 사용자가 이해한 것, 구현에 동의한 것은 서로 다르다.

## 시작

- `/start`의 기존 구조·문제 원인·변경안과 사용자 요구를 읽는다. 별도 리뷰를 요청해 받은 결과가 있으면 함께 본다.
  자료가 없으면 실제 코드와 소비자를 확인해 준비한다. 없는 구조를 만들어 설명하지 않는다.
- 이번 변경에 대해 사용자가 이미 설명한 내용과 질문에서 아는 부분·모르는 부분을 찾는다.
  경력이나 짧은 동의만으로 이해를 추정하지 않는다. 확인된 부분은 반복 설명하지 않는다.
- 기존 코드 설명만 원하면 `explain`의 역할이다. 여기서는 변경안을 이해·평가하고
  구현 범위를 합의한다. 읽기 전용 조사와 설명은 가능하지만 합의 전 구현하지 않는다.

## 설명

한 번에 한 흐름을 설명하고 질문을 받는다. 전체 파일 목록을 먼저 쏟아내지 않는다.

1. **현재:** 실제 사례 하나로 입력 → 처리 → 결과를 따라간다. 규칙·상태의 소유자와
   현재 문제의 원인을 짚고, 확인된 사실과 가설을 구분한다.
2. **변경 후:** 같은 사례에서 무엇이 유지·변경·신설되는지 겹쳐 보여준다. 이름과 책임,
   해당 파일·함수, 호출 관계를 대응시킨다. 스크립트라면 호출 시점·입력·출력·부작용도 설명한다.
3. **문제가 생기면:** 대표 실패 하나에서 어느 경계를 의심하고 어떤 코드·상태·로그를
   확인하면 원인을 구분할 수 있는지 설명한다. 아직 구현 전이면 예정된 확인 방법임을 밝힌다.
4. **선택:** 왜 이 변경이 필요한지, 더 단순한 대안과 비용, 이번에 바꾸지 않을 것을 설명한다.

작은 관계도나 짧은 코드 예시는 이해에 필요한 만큼만 쓴다. 설명은 채팅 안에서 끝내며
파일을 열어 알아서 이해하라고 넘기지 않는다.

## 이해도 확인과 보완

대화와 짧은 확인 질문을 바탕으로 **85점 이상 이해했는지 종합적인 인상으로 판단**한다.
정밀한 측정값이 아니다. 항목별 배점표·점수 계산·고정 문항 수는 만들지 않는다.

사용자가 자기 말로 동작을 설명하거나 결과를 예측하게 하고, 버그가 났을 때 어디부터
살펴볼지도 물어본다. 이미 대화에서 드러난 이해는 인정하고 부족해 보이는 부분만 확인한다.
질문은 짧게 나눠 실제 답변을 기다린다. 이름을 외우는 시험이나 정답에 동의만 받는 질문은 피한다.

85점에 못 미친다고 느껴지면 무엇이 아직 불분명한지 짚고, 다른 사례로 설명·질문을 이어간다.
사용자가 설계에 반대하는 것을 이해 부족으로 취급하지 않는다. 지적이 맞으면 내 설계를 고친다.
"알겠어"나 침묵만으로 충분히 이해했다고 판단하지 않는다. 사용자가 중단하면 남은 부분을
알리고 멈추며, 이해 확인을 마친 것으로 기록하지 않는다.

## 합의와 다음 단계

85점 이상으로 이해했다고 판단하고, 설명한 목표·구조·수정 범위에 사용자가 진행 의사를
밝히면 구현으로 넘어간다. 중요한 동작이나 버그 원인에 대한 오해가 남아 있으면 더 설명한다.
내 이해도 판단은 사용자의 구현 허락을 대신하지 않는다.

합의한 구조·범위와 이해도 판단 이유를 채팅에 짧게 남긴다. 인계가 필요하면 `handoff`의
기존 문서에 그 결과를 남긴다. 별도의 점수 파일이나 승인 기록 스크립트는 만들지 않는다.

구현 중 합의에 없던 책임·동작·범위가 필요해지면 그 부분만 다시 설명·확인·합의한다.
이미 이해하고 합의한 부분은 반복하지 않고, 합의 범위 안의 루틴 수정마다 처음부터 시험하지 않는다.
이해도 확인은 기술적 구조 리뷰나 구현 후 코드·구조·보안 리뷰를 대신하지 않는다.

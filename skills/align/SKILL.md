# align — 사용자의 분류와 실제 코드를 맞춘다

사용자가 설명에 동의하는 것을 넘어, 코드를 읽고 동작을 예상하며 버그의 원인을 추적할 수 있게 한다.
AI가 사용자의 분류를 이해했는지, 사용자가 코드를 이해했는지, 구현에 동의했는지는 별개다.

## 기존 코드와 사용자 관점

`start`의 조사 결과와 실제 코드·소비자를 읽는다. 자료가 없으면 이번 변경의 한 실행 경로부터
조사한다. 이미 확인한 이해·합의는 재사용하고, 기존 코드 설명만 요청하면 `explain`으로 답한다.

한 사례의 입력 → 처리 → 결과를 설명하며, 개념의 종류·책임 소유·호출 관계를 구분한다.
현재 파일 배치와 원하는 분류를 혼동하지 않는다. 사용자의 교정이 나오면 AI가 그 분류 원칙을
자기 말로 되짚고, 필요하면 인접 사례에 적용해 확인받는다. 폴더 이름만 따라 하는 것으로 끝내지 않는다.
분류가 실제 계약·의존성과 충돌하면 근거와 대안을 설명한다. 반대를 이해 부족으로 취급하지 않는다.

## 구현 전 합의

같은 사례에서 현재와 변경 후를 겹쳐 보여준다. 한 번에 전체 파일 목록을 쏟아내지 않는다.

- 책임과 폴더의 대응, 핵심 인터페이스의 이름·입력·반환·실패 방식.
- 새 분류·작성 패턴을 보여주는 대표 함수의 짧은 코드 초안. 아직 실행·검증된 구현은 아니다.
- 대표 오류가 생기면 의심할 경계와 확인할 코드·상태·로그. 구현 전이면 예정된 추적 방법이다.
- 더 단순한 대안, 변경 비용과 이번에 바꾸지 않을 범위.

사용자가 초안의 이름과 계약으로 동작을 예상할 수 있는지 확인한다. 이미 승인한 패턴을 그대로
사용하는 경우에는 사례를 연결하고 달라지는 부분만 설명한다. 모든 함수의 이름을 사전 승인받지 않는다.
설명과 초안은 채팅 안에서 보여주며, 파일을 열어 혼자 이해하라고 넘기지 않는다.

## 이해 확인과 구현 허락

대화에서 드러난 이해를 바탕으로 **85점 이상인지 종합적인 인상으로 판단**한다. 정밀한 측정값이
아니며 배점표·고정 시험·점수 파일을 만들지 않는다. 동작 예측이나 버그 추적에 남은 빈틈만 짧게
질문하고 실제 답변을 기다린다. 이미 설명한 이해를 반복해서 시험하지 않는다.

예상이 실제와 다르면 지식 부족인지, 이름·분류·상세 배치가 오해를 유발했는지 먼저 확인한다.
전자는 사례로 설명하고 후자는 설계를 고친다. 복잡한 코드를 설명으로 외우게 하는 것이 목표가 아니다.
짧은 동의·침묵을 충분한 이해로 간주하지 않는다. 사용자가 멈추면 미확인 부분을 알리고 멈춘다.

충분히 이해했다고 판단하고 사용자가 목표·구조·범위에 진행 의사를 밝힌 뒤 구현한다.
이해도 판단은 구현 허락을 대신하지 않는다. 합의 밖의 책임·동작·범위만 다시 맞추고,
루틴 수정이나 새 파일 하나마다 처음부터 재승인을 요구하지 않는다.

## 구현 후 코드 확인

검증·푸시한 작은 구현 단위에서 합의한 대표 함수의 실제 코드와 링크를 보여준다.
상위 흐름 → 필요한 하위 책임 순으로 읽고, 이름·입출력으로 예상한 동작을 본문과 대조한다.
대표 실패에서 어디부터 확인할지 실제 코드로 짚는다. 설계 이해나 테스트 통과를 코드 이해의
증거로 대신하지 않으며, 이는 독립적인 가독성 리뷰·QA 재현·보안 리뷰를 대체하지 않는다.

설명 없이는 막히는 지점은 위치, 예상과 실제의 차이, 변경·장애 대응 영향으로 구체화한다.
이번 경로에 필요한 정리만 제안하고 범위 밖 부채를 자동 수정하지 않는다. 인계가 필요하면
`handoff`에 합의·확인 근거와 미해결 지점을 남긴다. 사용자의 답변이 없으면 이해 확인은 미완료다.

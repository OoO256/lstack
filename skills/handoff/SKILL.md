# handoff.md 구조 및 작성 규칙

handoff.md 는 worklog 의 유일한 문서이자 **인간용 문서**다. 다음 작업하는 사람(사람 또는
subagent · compact 이후의 나)에게 넘기는 인계장이다.
경로: `docs/worklogs/YYYY-MM-DD-<slug>/handoff.md`.

계획은 이 문서에 쓰지 않는다 — **계획은 채팅에 인라인**으로 제시한다.

## 언제 쓰는가

- 계획 후 subagent 에 맥락을 넘겨야 할 때
- 구현 완료 후 PR 올리기 전 (`/pr` 이 이 문서를 desc 소스로 쓴다)
- 컨텍스트 윈도우가 차서 compact 하기 전
- 사용자가 `/handoff` 를 호출할 때

**파일은 하나, 매번 덮어쓴다.** 시점별로 누적하지 않고 항상 최신 상태만 남긴다.

## 구조

탑다운이다 — 위에서 아래로 읽으면 "왜 → 어떻게 → 무엇이 됐나 → 뭐가 남았나" 가 된다.

```markdown
# <goal 한 줄>

## 배경
현재 상황과 문제. 문제를 고치는 작업이면 원인 · 근본 원인까지.
처음 보는 동료가 맥락을 잡을 수 있게 2-3 문장.

## 해결 방법
탑다운 설계. as-is → to-be 와 그 사이를 잇는 구조 —
중심 개념 · 데이터 흐름 · 이해 단위 → 모듈/파일 매핑 (이름 한 줄 책임).
코드를 처음 여는 사람이 어디를 먼저 볼지 알 수 있게.

## 결과
실제로 바뀐 것. 독립 작업 단위별로 방침 중심 1-2 줄.
작업 중 내린 결정과 그 이유. 검증 방법(무엇을 돌리면 확인되는가).

## 한계와 후속
남은 리스크 · 알려진 한계 · 후속 작업. 없으면 "없음".
```

## 규칙

- **결과 중심, 과정 기록 금지.** 시도-실패-재시도, 어떤 순서로 했는지는 쓰지 않는다.
  단 "왜 그 결정을 했는가" 는 `## 결과` 에 남긴다 — 다음 사람이 되묻지 않게.
- **시점에 따라 빈 섹션이 생기는 게 정상이다.** 계획 직후면 `## 결과` 가 비고
  `## 해결 방법` 이 가득하다. 빈 섹션은 "없음" 한 줄로 남기고 지우지 않는다.
- **인간용 글쓰기 (의도 7):**
  - 방침 중심 — "왜 / 어떤 결정" 위주. 파일·함수 나열 X (필요하면 한두 줄로 압축).
  - 외부 가독성 — 이 작업 안 한 동료가 처음 읽고 이해 가능하게. 사내 약어 · "아까 그거" 식 지시 금지.
  - UI/UX 변경은 캡처 이미지를 첨부한다.
- 구조 영향(새 이해 단위 · 모듈 경계 변경)이 있으면 `## 해결 방법` 에 매핑과 기존 구조
  적합성 판정(`수용 가능` 또는 `선행 리팩토링 필요 — 이유`)을 함께 쓴다 (의도 8).

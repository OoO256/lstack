# handoff.md 구조 및 작성 규칙

handoff.md 는 worklog 의 유일한 문서이자 **인간용 문서**다. 다음 작업하는 사람(사람 또는
subagent · compact 이후의 나)에게 넘기는 인계장이다.
경로: `docs/worklogs/YYYY-MM-DD-<slug>/handoff.md`.

다음 사람이 무엇을 구현했는지뿐 아니라 왜 이 방향을 골랐고 무엇을 아직 고민해야 하는지 알 수 있어야 한다.
계획 제시와 합의는 채팅에서 한다. handoff는 그 대화를 대신하지 않으며, 결정된 내용과 판단 근거를 보존한다.

## 언제 쓰는가

- 계획 후 subagent 에 맥락을 넘겨야 할 때
- 구현 완료 후 PR 올리기 전 (`/pr` 이 이 문서를 desc 소스로 쓴다)
- 컨텍스트 윈도우가 차서 compact 하기 전
- 사용자가 `/handoff` 를 호출할 때

**작업당 파일은 하나다.** 상태는 최신으로 갱신하되 여전히 유효한 결정 이유를 지우지 않는다.
결정이 바뀌면 현재 결론을 먼저 쓰고, 다음 판단에 필요한 이전 선택·변경 이유만 짧게 보존한다.

## 구조

탑다운이다 — 위에서 아래로 읽으면 "왜 → 어떻게 → 무엇이 됐나 → 뭐가 남았나" 가 된다.

```markdown
# <goal 한 줄>

## 배경
사용자의 실제 경험과 문제, 줄이려는 비용과 성공 기준. 확인된 원인과 가설을 구분한다.
처음 보는 사람이 문제의 의미를 이해할 만큼 간결하게 쓰되, 문장 수 때문에 중요한 맥락을 버리지 않는다.

## 해결 방법
탑다운 설계. as-is → to-be 와 그 사이를 잇는 구조 —
중심 개념 · 데이터 흐름 · 이해 단위 → 모듈/파일 매핑 (이름 한 줄 책임).
코드를 처음 여는 사람이 어디를 먼저 볼지 알 수 있게.
왜 이 방향을 선택했는지, 다시 제안될 만한 중요한 대안을 선택하지 않은 이유를 남긴다.
모든 아이디어를 나열하지 말고 판단을 바꾼 사용자 피드백·실패 경험과 비용의 차이를 연결한다.

## 결과
실제로 바뀐 것. 독립 작업 단위별로 방침 중심 1-2 줄.
작업 중 내린 결정과 그 이유. 검증 방법(무엇을 돌리면 확인되는가).
합의한 방향·실제로 구현된 것·검증된 효과를 구분한다. 사용자 명시 요구와 AI의 해석을 섞지 않는다.
align에서 합의한 분류·용어·대표 코드와 실제 코드 이해를 확인한 근거가 있으면 짧게 연결한다.
설명하지 않았거나 답변을 받지 않은 이해를 확인 완료로 기록하지 않는다.
구현 피드백이 있으면 [compound의 기록 기준](../compound/references/feedback.md)을 읽고
교정 근거·적용 범위·확정 여부와 수정 위치를 남긴다.

## 한계와 후속
남은 리스크 · 알려진 한계 · 후속 작업. 없으면 "없음".
이해부채는 막힌 코드 위치·예상과 실제의 차이·변경 또는 장애 대응 영향·다음에 다룰 시점으로 남긴다.
승인되지 않은 일반화는 개선 후보로 구분한다. 새 점수판이나 별도 피드백 파일은 만들지 않는다.
아직 풀리지 않은 질문과 어떤 관찰·요구 변화가 생기면 현재 결정을 재검토할지 적는다.
다음 대화가 이미 끝난 논쟁이 아니라 이 질문에서 시작할 수 있어야 한다.
```

## 규칙

- **작업 일지는 생략하고 판단 근거는 보존한다.** 명령·도구 실행 순서는 생략하되,
  선택을 바꾼 실패·교정과 버린 대안의 이유는 남긴다. Git 이력을 찾아야만 이유를 알 수 있게 하지 않는다.
- **관련 기록을 연결한다.** 여러 PR이 같은 고민에서 나왔다면 공통 배경은 대표 handoff 한 곳에 두고,
  각 기록은 그 링크와 자기 결정·차이만 남긴다. 서로 다른 판단의 책임을 한 문서로 뭉치지는 않는다.
- **근거는 필요한 만큼만 연결한다.** 짧은 사용자 발언·관련 PR·코드 위치를 사용하고, 정확한 원문이
  중요할 때만 확인 가능한 세션 위치를 보조로 남긴다. 원문 전체·민감정보는 복사하지 않는다.
  링크나 로컬 세션에 접근하지 못해도 핵심 이유와 남은 질문은 이 기록에서 이해할 수 있어야 한다.
- **시점에 따라 빈 섹션이 생기는 게 정상이다.** 계획 직후면 `## 결과` 가 비고
  `## 해결 방법` 이 가득하다. 빈 섹션은 "없음" 한 줄로 남기고 지우지 않는다.
- **인간용 글쓰기:**
  - 방침 중심 — "왜 / 어떤 결정" 위주. 파일·함수 나열 X (필요하면 한두 줄로 압축).
  - 외부 가독성 — 이 작업 안 한 동료가 처음 읽고 이해 가능하게. 사내 약어 · "아까 그거" 식 지시 금지.
  - UI/UX 변경은 캡처 이미지를 첨부한다.
- 구조 영향(새 이해 단위 · 모듈 경계 변경)이 있으면 `## 해결 방법` 에 매핑과 기존 구조
  적합성 판정(`수용 가능` 또는 `선행 리팩토링 필요 — 이유`)을 함께 쓴다.

마지막으로 기록과 직접 연결한 공통 배경을 읽고, 이미 버린 접근을 반복하지 않으면서 남은 질문부터
대화를 시작할 수 있는지 확인한다. 형식 검사나 기록 작성 완료를 실제 인계 효과의 검증으로 부르지 않는다.

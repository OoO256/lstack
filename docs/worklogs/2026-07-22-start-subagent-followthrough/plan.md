# start 계획 승인 후 저가 구현 위임 보장

## 배경

as-is: `start`는 계획 확인 뒤 병렬·저가 위임을 "판단으로" 한 줄만 언급해, 다음 턴의 짧은 승인 발화가
새로운 skill activation으로 이어지지 않으면 실행 원칙이 유실될 수 있다. 그 결과 상위 메인이 큰 구현까지
직접 수행하고 사용자가 뒤늦게 위임 누락을 지적해야 했다.

to-be: 계획 승인을 `start` continuation으로 명시하고, 구현 전 규모·파일 경계를 판단한다. 상위 메인 모델과
300줄 이상 예상 구현의 조합에서는 충돌 없는 구현을 저가 서브에이전트로 위임하고, 메인은 감독·통합·검증에
집중한다. 위임하지 않을 때도 구체적인 이유를 남겨 결정이 보이게 한다.

## 계획

### T1: `start` 승인 continuation과 실행 인계 명시 ✅
짧은 계획 승인 발화를 `start`의 후속 턴으로 인식하고, 예상 diff 구간과 파일 소유권을 바탕으로 위임 여부를
결정·보고하도록 했다. 같은 파일·공유 계약은 순차 처리해 병렬 구현 충돌을 피한다.

### T2: 개발 원칙과 아키텍처 동기화 ✅
상위 메인 모델(fable/sol 계열)과 예상 300줄 이상 구현에서 Sonnet/Terra급 위임을 기본값으로 명시하고,
메인의 책임을 계획·감독·통합·검증으로 한정했다.

### T3: 플러그인 구조와 문서 계약 검증 ✅
strict plugin validation, JSON, frontmatter, 내부 링크, whitespace 검증을 통과했다. prompt 문구 자체를
미러링하는 change-detector 테스트는 남기지 않았다.

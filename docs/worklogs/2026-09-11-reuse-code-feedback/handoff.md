# 교정의 근거를 다음 구현과 리뷰에서 재사용한다

## 배경

[사용자 경험과 공통 선택 이유](../2026-09-11-align-code-reading/handoff.md)를 먼저 읽는다.
세션 끝에 개선을 제안하는 것만으로는 다음 작업이 사용자 피드백을 읽고 적용하는지 알 수 없다.
반복 지적을 범위 없는 규칙으로 추가하면 오히려 새로운 이해·리뷰 비용이 생긴다.

## 해결 방법

기존 구조는 수용 가능하다. compound(변경)는 교정의 근거·범위·확정 여부와 개선 제안을 소유하고,
start·reviewer(변경)는 관련 승인 기준을 조회한다. pr·handoff(변경)는 기존 작업 기록에 결론을 남긴다.
승인된 프로젝트 분류·사례는 해당 책임 문서, 공통 작성 방식은 lstack 담당 스킬이 소유한다.

전체 세션 수집기·별도 점수판 대신 기존 기록과 담당 문서를 재사용해 읽을 맥락을 제한했다.
AI가 교정을 일반화한 즉시 규칙으로 적용하면 국소적인 선택이 영구 제약이 될 수 있어,
현재 요구·향후 명시 기준·승인 전 후보를 구분하고 하니스 수정 승인을 유지했다.

## 결과

- 같은 원인의 교정을 최신 결론으로 합치고, 이번 요구·향후 명시 기준·AI의 일반화 후보를 구분한다.
  조회는 현재 경로·책임과 관련된 프로젝트 지침·handoff로 좁힌다. 전역 메모리나 대화 수집기는 만들지 않았다.
- 재발 원인을 미참조·오해·구현 이탈·기준 오류로 나누어 기존 기준을 보완·축소·폐기하도록 했다.
  승인 전 일반화와 하니스 수정·설치·외부 게시를 자동 실행하지 않는다. harness-sage의 자동 issue/PR 게시도 제거했다.
- 이번 작업의 교정: 사용자는 “기존 pr 말고 새로 pr”를 요구했다. 세 PR은 main에서 시작하는 새 스택이며
  기존 #24는 기반이 아니다. 이 선택은 이번 작업의 범위이지 stacked PR 일반 금지 규칙이 아니다.
- 최초 PR 작성 시 검증: 전체 스킬 12개 형식, 활성 문서 상대 링크 34개, git diff --check 통과.
  작성자가 승인되지 않은 일반화·사례 부재·현재 지시와 충돌·읽기 전용 리뷰·종료 직전 피드백을 지침과 대조했다.

## 한계와 후속

- [PR #28](https://github.com/OoO256/lstack/pull/28)은 #27 위에 쌓는 세 번째 PR이다.
  피드백 절차는 스킬 지침 기반이며 매번 실행을 강제하는 hook가 아니다.
- 실제 세션 간 재사용과 교정 시간 감소는 미검증이다. 다음 관련 작업의 코드 예측·버그 추적·재교정으로 확인해야 한다.
- lint·독립 리뷰·실제 에이전트 실행 시험은 하지 않았다. 설치본·제품 코드·테스트·버전은 변경하지 않았다.
- 기존 #24는 사용자 요청으로 닫혔다. 이름 변경·PRINCIPLE 정리 등은 #26·#27에 반영되어 있다.
- 사용자는 결과뿐 아니라 이 대화의 고민을 다음 수정 때 이어가길 원했다. 최신 결론만 남기는
  기록의 한계와 보완은 [판단 맥락 인계](../2026-09-11-preserve-handoff-reasoning/handoff.md)에서 다룬다.
- 다음 관련 작업이 승인 기준을 실제로 찾는지, 같은 교정이 재발하는지 아직 모른다.
  재발하면 새 규칙을 추가하기 전에 미참조·오해·구현 이탈·기준 오류 중 무엇인지 확인한다.

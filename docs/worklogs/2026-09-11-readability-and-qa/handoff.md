# 읽기 비용·동작 재현·보안으로 검토 책임을 나눈다

## 배경

[공통 사용자 경험](../2026-09-11-align-code-reading/handoff.md)과
[이전 리뷰 구성의 이유](../2026-09-11-review-code-understanding/handoff.md)를 함께 본다.
사용자는 code-reviewer와 structure-reviewer의 경계가 불분명하고 code-reviewer의 필요성이 낮다고 판단했다.
code-reviewer를 없애고 structure-reviewer는 readability-reviewer로 바꾸며, 기획·경계 사례를
독립 작업 공간에서 재현하고 비용·성능·지연 위험을 판단하는 QA를 추가하라고 요청했다.
이후 사용자는 리뷰 전에 구현자가 원칙을 주입받고 지키는 편이 낫다고 지적했다. start는 이미
원칙 읽기와 align을 연결했지만, 구체적인 구현 선택·위임 전달·작성 중 대조가 약하다는 분석에 따라
이 세 부분을 보강하도록 승인했다. 리뷰 후 교정보다 잘못된 패턴의 확산을 먼저 줄이는 것이 목적이다.

## 해결 방법

기존 구조는 수용 가능하다. reviewer(변경)는 사용자 요청에 따라 세 역할을 새 context에서 호출한다.
readability-reviewer(개명)는 사람이 분류·이름·흐름을 읽는 비용, behavior-tester(신설)는 실행 결과와 측정,
security-reviewer(유지)는 악용 가능성을 맡는다. 코드의 동일한 부분을 보더라도 판단과 증거가 다르다.

처음 이름은 qa였으나, 사용자가 실제 실행 역할을 드러내는 behavior-tester를 승인했다.
품질 전반을 뜻하는 QA나 실행 여부가 드러나지 않는 behavior-reviewer 대신, 직접 동작을 시험한다는
이름을 택했다. 역할·권한은 유지하고 정의 파일·식별자·호출·문서 참조를 함께 개명했다.

포괄적인 코드 리뷰 역할을 남긴 채 체크리스트만 더 나누는 대신, 읽기 판단과 동작 재현을 분리했다.
QA도 정적 추측으로 끝내거나 기존 테스트 통과만 확인하면 차이가 없어지므로,
요구에서 기대값을 정하고 코드에서 실패 가설을 도출해 직접 재현한다.

QA에는 임시 테스트·fixture·계측을 작성할 권한이 필요하지만 제품 수정 권한은 필요하지 않다.
별도 worktree도 외부 DB·유료 API를 격리하지 못하므로, 기본은 로컬 데이터·대역을 사용하고
실서비스·공유 데이터·유료 호출은 승인된 대상·한도 안에서만 실행하도록 했다.
미커밋 변경을 빠뜨린 HEAD만 시험하지 않도록 검토 대상과 작업 복사본의 내용 일치도 확인한다.

구현 전·중 적용은 start가 소유한다. 원칙을 이번 책임·이름·대표 코드의 선택으로 구체화하고,
위임·재개 때 원본 지침과 승인 근거를 전달·대조하며, 첫 실행 경로부터 실제 diff와 기대 동작을 확인한다.
작성 원칙을 복제하거나 자동 리뷰·추가 승인 단계를 만들지 않는다. 기존 align의 합의와 handoff를 재사용한다.

## 결과

- code-reviewer 정의를 제거하고 structure-reviewer를 readability-reviewer로 개명했다. 이전 내용은 Git에서 복구 가능하다.
- QA에 정상·경계·실패 사례 도출, 독립 재현, 비용·성능·지연의 실측과 추정 구분, 실행 한도·중단·정리 기준을 넣었다.
  기획이 불명확하거나 재현이 막힌 경우를 통과로 보고하지 않으며, 제품 코드를 수정해 통과시키지 않는다.
- reviewer의 역할별 호출·입력·결과 처리, start·align과 아키텍처 인덱스를 연결했다.
  사용자 요청 실행은 유지하며, 자동 QA 완료 강제나 검사 스크립트는 만들지 않았다.
- 검증: 변경 스킬 3개 형식·에이전트 3개 YAML·활성 문서와 연결된 작업 기록의 상대 링크 47개·
  git diff --check 통과. 활성 호출·지침에 제거한 에이전트 이름이 남지 않았음을 확인했다.
  작성자가 미커밋 변경·실행 환경 부재·유료 호출·제품 수정 금지·측정 근거를 지침과 대조했다.
  lint나 실제 독립 에이전트 실행 시험은 하지 않았다.
- 개명 후 검증: 변경 스킬 3개 형식·변경 문서 상대 링크 35개·git diff --check 통과.
  behavior-tester 정의는 이름·제목 외 기존 qa 내용과 같고, 활성 식별자·파일 참조에 옛 이름이 없음을 확인했다.
- start에 구현 선택의 구체화, 위임·재개 시 원칙과 합의의 전달, 작은 구현 단위별 자기 점검을 연결했다.
  합의 안의 이탈은 구현자가 교정하고 계약·범위 변경만 다시 합의한다. 독립 리뷰 수동 호출 방침은 유지한다.
  보강 검증: start 스킬 형식·변경 문서 상대 링크 5개·git diff --check 통과. 작성자가 단순 수정·
  위임·세션 재개·합의와 현재 코드 충돌 시의 지침을 대조했으며 실제 에이전트 실행 시험은 하지 않았다.

## 한계와 후속

- #29 뒤에 추가하는 PR이며 이전 PR 브랜치는 변경하지 않는다. 제품 코드·테스트·설치본·버전은 변경하지 않았다.
- start 보강으로 실제 준수율이 개선됐는지는 미검증이다. 다음 적용에서 첫 경로의 이탈을 확장 전에
  교정하는지, 위임·재개 뒤 합의가 유지되는지 확인한다. 반복 보고가 늘면 기준을 추가하기보다 중복 보고부터 줄인다.
- 실제 QA 에이전트의 실행 재현과 환경 격리는 아직 미검증이다. 다음 실행에서 요구 누락·타임아웃·
  중복 요청 같은 실제 경로의 사례를 도출하는지, 원본 변경 없이 재현하고 근거를 남기는지 확인해야 한다.
- 가독성 지적과 QA 결과가 계속 중복되면 새 리뷰어를 늘리기보다 어느 판단·증거가 겹치는지부터 조정한다.
  재현 불가 항목이 많으면 먼저 테스트 환경·관측 수단의 부족을 확인한다. 검증 불가를 자동 수정 권한으로 확대하지 않는다.

# 합의한 분류와 읽기 방식을 독립 리뷰한다

현재 구성은 readability-reviewer·qa·security-reviewer다. 아래는 최초 역할 분리의 근거이며,
code-reviewer 제거와 구조 리뷰 개명의 이유는 [후속 결정](../2026-09-11-readability-and-qa/handoff.md)을 읽는다.

## 배경

[사용자 경험과 공통 선택 이유](../2026-09-11-align-code-reading/handoff.md)를 먼저 읽는다.
설계에서 읽기 방식을 합의해도 실제 구현이 그 기준을 지키는지는 별도 확인이 필요하다.
기존 리뷰는 코드·보안 중심이며 함수 줄 수 같은 일률적인 기준과 리뷰 후 수정 지시가 섞여 있었다.

## 해결 방법

기존 구조는 수용 가능하다. code-review 스킬은 reviewer로 이름을 바꾸고 요청 범위의 독립 검토를 맡는다.
code-reviewer(변경)는 동작·오류, structure-reviewer(신설)는 분류·계약·읽기 비용,
security-reviewer(유지)는 악용 가능성을 맡는다. 작성 기준은 앞선 PR의 start 참고 문서를 재사용한다.

구현자에게 자기 해설을 검증시키는 대신, 같은 사용자 기준을 받은 새 context가 실제 코드를 읽도록 했다.
이 분리는 사용자가 이해했음을 보장하지 않으며, 형식적인 줄 수 제한 대신 예상과 실제의 차이를 근거로 삼는다.

## 결과

- 명시한 사용자 요구·승인 사례를 공통 입력으로 전달하고 구현자의 해설과 구분한다.
  구조 리뷰는 이름·입출력에서 예상한 동작을 실제 구현·소비자와 대조한다.
- 함수 줄 수·문제 개수 제한을 제거하고, 근거가 있는 요구 위반과 취향·미확인을 구분한다.
  리뷰는 수동 실행이며 수정·lint·재리뷰·외부 게시 권한을 자동으로 얻지 않는다.
- 최초 PR 작성 시 검증: 변경 스킬 2개 형식, 활성 문서 상대 링크 29개, git diff --check 통과.
  작성자가 설계만 요청, 역할 지정, 승인 사례 부재, 기존 부채 발견, untracked 변경 포함을 지침과 대조했다.

- 피드백 재사용은 [세 번째 PR 기록](../2026-09-11-reuse-code-feedback/handoff.md)에서 이어진다.
  설치본·제품 코드·테스트·hook는 변경하지 않았다.
- 다음 질문은 리뷰가 실제 오해를 유발하는 이름·경계를 잡는지, 단순 취향 지적을 늘리는지다.
  취향 지적이 반복되면 리뷰 횟수를 늘리기보다 근거 기준·승인 사례를 보완한다.

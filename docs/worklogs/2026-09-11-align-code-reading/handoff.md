# 설계 설명을 실제 코드 이해로 연결한다

## 배경

사용자는 소규모 팀의 리드 개발자로 구현을 AI에 맡기되, 코드를 읽고 수정·장애 대응을 책임지고 싶다.
인터뷰와 해결책 설명은 이해되지만 코드의 분류·이름·상세 배치가 사용자의 관점과 달라, 구현 후
해석하면서 반복 교정하는 데 시간이 든다고 설명했다. 핵심 발언은 “대화만 이해해서는 내가 코드베이스를 책임진다고 말할 수 없다”였다.

사용자는 계층·역할에 따른 추상화와 규칙적인 폴더·인터페이스, 동작을 정확히 드러내는 이름,
문단처럼 읽히는 함수를 원한다. 긴 수동 타입 검사와 범용 기능 재구현은 스키마·기존 라이브러리로
줄이길 원했다. 목표는 코드 생성량이 아니라 실제 코드 이해·버그 추적을 유지하면서 재교정 비용을 줄이는 것이다.

초기에는 lint·리뷰 완료 강제 장치를 만들었으나, 변경이 너무 많고 장치의 역할·실패를 이해하고
리뷰하는 부담이 생겼다. 사용자는 “그냥 내가 수동으로 돌린다”며 범위를 줄였다.
이 대화의 원인 판단은 설계 설명의 이해와 실제 코드 이해를 혼동했고, AI가 사용자의 분류를
이해했는지 확인하기 전에 구현했다는 것이다. AI의 context window가 원인이라는 설명은 검증한 사실이 아니다.

## 해결 방법

기존 구조는 수용 가능하다. start(변경)는 현재 코드·원인과 대표 코드 초안을 준비하고,
align(신설)은 사용자 분류·인터페이스·읽기 방식을 합의하며 구현 후 실제 코드로 확인한다.
작성 원칙은 start의 참고 문서, 공유는 pr, 기록은 handoff가 소유한다.

선택 이유와 보류한 대안:

- 설명만 늘리면 이해하기 어려운 코드를 사용자에게 외우게 할 수 있다. 먼저 AI가 분류 원칙을
  되짚고 대표 코드로 합의하며, 구현 뒤 실제 동작·버그 추적과 대조하기로 했다.
- 자동 lint·리뷰 완료 차단은 당장 재도입하지 않는다. 수동 실행으로 장치의 이해 부담을 줄이고,
  실제 반복 누락이 관찰되면 그 문제 범위에서만 자동화를 다시 논의한다. 기존 필수 CI를 해제하는 결정은 아니다.
- 추상화 수·함수 줄 수를 줄이는 것 자체를 목표로 삼지 않는다. 사용자가 원하는 책임 계층을
  보존하되, 통과 계층과 불필요한 탐색은 줄인다. 저장소 전체 정리 대신 한 실행 경로씩 개선한다.
- 85점은 사용자가 요청한 종합적인 인상이다. 세분화된 배점표는 복잡도를 늘려 제외했으며,
  설계 동의나 구현 승인을 실제 코드 이해의 증거로 쓰지 않는다.

## 결과

- align에 AI의 분류 되짚기, 대표 코드 합의, 이름으로 예상한 동작·버그 추적의 실제 코드 대조를 추가했다.
  85점은 종합적인 인상이며, 사용자 응답 없는 이해·구현 허락을 만들어내지 않는다.
- 이름·캐스팅·추상화 수준·스키마·기존 라이브러리 활용 기준을 작성 전에 읽도록 연결했다.
  PRINCIPLE 문서는 제거하고 시작·검증·소통·문서 원칙을 담당 스킬에 배치했다. Git에서 복구 가능하다.
- 최초 PR 작성 시 검증: 변경 스킬 5개 형식 확인, 활성 문서의 상대 링크 23개, git diff --check 통과.
  질문만 받은 경우, 승인 패턴 재사용, 잘못된 이름이 오해를 만든 경우, 코드 확인 답변이 없는 경우를
  작성자가 지침과 대조했다. 실제 에이전트 실행 시험은 아니다.

  작업마다 반복되어 오히려 부담을 늘리지는 않는가? 후자라면 이미 확인한 패턴의 반복 설명·질문을 줄이는 쪽부터 검토한다.

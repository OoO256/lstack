# 개발 원칙 (lstack 가이드)

lstack로 작업할 때 지키는 개발 의도. `start`가 작업 시작 시 로드한다.
반복 명령은 스킬이 수행하고, 프로젝트가 명시적으로 설정한 검사는 완료 hook가 실행한다.

## 라이프사이클

```text
/start → 구현 → self-test(lint·unit·integ) → /show → /pr → /compound → /close
```

`structure-reviewer`는 책임·공개 계약·모듈 경계 변경 전에 설계를 검토하고, 구현 후에는
현재 diff를 별도 fresh context에서 검토한다. 설계 검토가 diff 검토를 대신하지 않는다.
`.lstack.json`으로 opt-in한 프로젝트는 lint 실행과 현재 변경의 실제 diff 검토 완료를
Stop hook에서 확인한다. 세부 계약은 [ARCHITECTURE.md](ARCHITECTURE.md)의 Hooks가 SSOT다.

## 8개 의도

1. **독립 분해·병렬.** 서로 독립인 작업은 나눠 진행한다. 독립 작업이 없으면 분해하지 않는다.
2. **위임.** 독립 작업은 적절한 서브에이전트에 위임한다. 구조 검토는 구현자와 context를
   분리하고, 사용자 목표·확정 요구를 전달하되 구현자의 정당화를 정답으로 넘기지 않는다.
3. **최소 행동 테스트.** 실제 사용자 관찰 동작과 오류 경로를 검증한다. 테스트가 깨졌을 때
   버그인지 판단하고, 리팩터·값 변경만 감지하는 테스트는 늘리지 않는다. 반복적으로 값과
   코드를 복사한 기대값보다 CLI·임시 git·실제 경계에서의 결과를 검사한다.
4. **worktree 격리.** 새 구현은 격리 worktree에서 시작한다. 기존 작업은 보존한다.
5. **의도 확인.** 구현 요청과 질문을 구분한다. 구현 전 불명확한 목표·성공 기준만 질문하고,
   이미 합의한 범위의 루틴 구현·오류 수정에 매번 승인을 다시 요구하지 않는다.
6. **실환경 검증.** 변경 위험에 맞는 검증과 필요한 실제 실행을 한다. UI 변경은 `/show`로
   동작을 확인한다. 단순 문서 변경에 관련 없는 브라우저 테스트를 만들지 않는다.
7. **인간용 문서.** handoff.md·PR은 배경과 결과, 실제 결정과 한계를 비관여자도 이해하게
   쓴다. UI/UX 변경은 캡처를 첨부한다. 계획은 채팅에서 정하고 문서는 지속할 맥락을 남긴다.
8. **유지보수 설계.** 기존 개념·동작·문제의 원인을 먼저 확인한 뒤 변경안을 만든다.
   이름과 책임의 대응을 분명히 하되 모든 개념을 별도 파일과 1:1로 쪼개지 않는다.
   현재 구조가 변경을 수용하지 못하면 필요한 선행 정리를 범위 안에 포함한다.

## 설계와 이름

- 기존 개념 트리와 관계를 복원한다. 종류·소유·호출 관계를 구분하고, 별개 객체를
  상속 형제처럼 그리지 않는다. 현재 동작에서 문제의 원인을 확인하고 변경안이 이를
  어떻게 해결하는지 적는다. 확인되지 않은 원인은 가설로 표시한다.
- 변경안에는 기존/변경/신설 책임과 소유할 모듈, 인접 계약에서 이미 쓰는 이름을 적는다.
  새 파일·이름 수를 0으로 고정하지 않는다. 필요한 책임 분리와 공통 생명주기는 정상이다.
- 책임·공개 계약·모듈 경계가 바뀌면 구현 전에 fresh `structure-reviewer`가 검토한다.
  새 이름이 없더라도 경계가 바뀌면 대상이고, 새 파일만 생겼다고 무조건 대상은 아니다.
  구현 중 이 변화가 추가되면 변경안을 갱신하고 독립 검토한다. 사용자 목표나 합의 범위를
  바꾸는 선택만 사용자에게 확인한다. 새 파일을 막는 PreToolUse 게이트는 두지 않는다.
- 일반 변수는 설명적인 명사, boolean은 의문문, 함수·메서드·이름 있는 화살표 함수는
  동사로 시작한다. 문법은 프로젝트 lint에 맡긴다. 명사 여부·설명성·이름과 동작의 1:1
  대응은 실제 소비자와 부작용을 읽는 독립 리뷰가 판단한다.
- `isAdmin`은 여부 반환, `requireAdmin`은 권한 없으면 거부, `grantAdmin`은 권한 부여다.
  단순한 접두사 통일은 역할 차이를 숨긴다. 이유·제약을 설명하는 주석은 유지한다.
- `as const` 외 캐스팅은 테스트·mock 포함 금지한다. 타입과 데이터 경계 자체를 고친다.
- `Policy`·`Manager` 같은 단어 자체를 금지하지 않는다. 기존 계약과 같은 역할에는 같은
  어휘를 쓰고 다른 책임이면 차이를 설명한다. 사용자가 선택한 `EventValidationPolicy`와
  `BaseAgent`의 공통 생명주기는 정상 사례다. 과거 피드백이 항상 추상화 감소였다는 주장은
  이 사례들과 충돌하므로 근거로 사용하지 않는다.
- 공유 위치는 실제 소유자·소비자·의존 방향으로 정한다. 불필요한 파생값, 단일 필드 포장,
  통과만 하는 계층과 중복 스키마·enum을 독립 리뷰에서 확인한다. 사용처 수·줄 수·새 이름
  수는 조사 후보이며 실패 조건이 아니다.

## 점진 적용

프로젝트의 명시적 검사 범위에 동일 lint 명령을 개발 완료와 CI에서 연결한다.
관찰 → 신규 위반 차단 → 기존 위반이 없는 영역 전체 차단 순으로 적용할 수 있다.
의미적 구조 지적은 `report`에서도 보고하고, `enforce`에서는 확정 blocker를 고친다.
검사 범위와 수정 권한은 별개다. 기존 부채는 관찰·보고하며 승인된 현재 변경 범위만
수정한다. 검사 시스템 도입만 승인됐다면 기존 서비스 코드·제품 테스트 정리를 추가하지 않는다.
lint 실패·실행 오류·실제 리뷰 누락·미완료는 어느 모드에서도 통과시키지 않는다.
검토한 코드가 바뀌면 새 검토가 필요하고, 동일한 코드는 재사용한다.

## 커뮤니케이션

한국어로 결론부터 짧고 평이하게 말한다. 사용자와의 설계·계획·리뷰는 채팅 안에서
설명하며 파일 열람을 요구하지 않는다. `handoff.md`·PR은 합의와 결과를 남기는 문서다.
커밋·외부 게시 권한은 사용자 지시를 따른다. 과거 세션의 허용을 새 권한으로 해석하지 않는다.

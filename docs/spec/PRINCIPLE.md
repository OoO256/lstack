# 개발 원칙 (lstack 가이드)

lstack 로 작업할 때 항상 지키는 개발 의도. `start` 가 작업 시작 시 이 파일을 컨텍스트에 로드한다.
고정 스테이지·검증 게이트는 없다 — 아래 의도를 **판단으로** 지키고, 반복되는 명령은 스킬이 대신 발동한다.

## 라이프사이클

```
/start → 구현 → self-test(unit·integ) → /show(①/②) → /pr → /compound(자동·제안만) → /close
                                                              /review = 남의 PR 볼 때 아무 때나
```

이 흐름은 **기본 arc 일 뿐 강제 게이트가 아니다.** 스킬은 "반복 명령 묶음"이고,
중간 구현은 이 가이드를 지닌 채 메인 컨텍스트가 판단으로 진행한다.

## 8개 의도

1. **독립 분해 · 병렬.** 작업을 서로 독립인 단위로 쪼개 병렬로 진행한다.
   독립 read-only 다항 작업(분류 · 조사 · 벤치마크 · 다파일 탐색)은 "할까 말까" 판단 대상이 아니라 **기본으로 fan-out** 한다.
   단, 공유 worktree 에서의 write(구현·수정)는 충돌 방지를 위해 순차로 한다 — 병렬은 read-only 에 쓴다.
2. **저가 위임 · 모델 티어링.** 서브태스크는 더 저렴한 서브에이전트로 위임하되 작업 성격에 맞춰 티어를 고른다 —
   고volume · 저판단(기계적 추출 · 분류)은 haiku, 종합 · 판단이 필요한 단계는 sonnet.
3. **TDD · 최소 테스트.** TDD 로 구현·검증하고, 완료 후엔 동작을 보장하는 **최소 테스트셋**만
   남기고 불필요한 케이스는 제거한다.
4. **worktree 격리.** 항상 origin/main 에서 worktree 새 브랜치로 시작한다. (`start` 가 강제)
5. **의도 인터뷰.** 구현 전 불명확한 의도를 인터뷰로 명확히 한다. (`start` 가 강제)
6. **실환경 e2e.** 마지막에 실환경 e2e(로컬 서버 + Chrome CDP)로 동작을 검증한다. (`show`)
7. **인간용 문서.** plan.md · PR 은 사람이 이해하기 위한 것 — 독립 작업별로 그룹화하고,
   as-is → to-be 로 설명하고, 이 작업을 안 한 사람도 이해할 만큼 평이하게 쓰고,
   UI/UX 변경은 캡처 이미지를 첨부한다.
8. **유지보수 설계.** 단순화 · SRP · 응집도↑/결합도↓ · SSOT · 적당한 수의 위계를 항상 고려한다.

## 커뮤니케이션

사용자와의 설계·계획·리뷰는 **대화(채팅) 안에서 인라인**으로 한다.
내용을 별도 md 로 만들어 "열어보라"고 넘기지 않는다 —
파일(plan.md · PR desc)은 durable 기록/산출물로만 쓰고, 리뷰를 위해 파일 열람을 요구하지 않는다.

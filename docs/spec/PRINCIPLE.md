# 개발 원칙 (lstack 가이드)

lstack 로 작업할 때 항상 지키는 개발 의도. `start` 가 작업 시작 시 이 파일을 컨텍스트에 로드한다.
고정 스테이지·검증 게이트는 없다 — 아래 의도를 **판단으로** 지키고, 반복되는 명령은 스킬이 대신 발동한다.

## 라이프사이클

```
/start → 구현 → self-test(unit·integ) → /show(①/②) → /pr → /compound(자동·제안만) → /close
                                                              /review = 남의 PR 볼 때 아무 때나
```

이 흐름은 **기본 arc 일 뿐 강제 게이트가 아니다.** 스킬은 "반복 명령 묶음"이고,
중간 구현은 이 가이드를 지닌 채 메인 컨텍스트가 판단으로 진행한다.

## 8개 의도

1. **독립 분해 · 병렬.** 작업을 서로 독립인 단위로 쪼개 병렬로 진행한다.
2. **저가 위임.** 서브태스크는 더 저렴한 서브에이전트(Sonnet/Terra 등)로 위임한다.
   특히 메인이 상위 모델(fable/sol 또는 동급)이고 예상 구현 diff 가 300줄 이상이면,
   메인은 계획·감독·통합·검증에 집중하고 구현 위임을 기본으로 한다. 같은 파일이나 공유 계약을
   동시에 수정하지 않도록 파일 경계를 나누고, 경계를 나눌 수 없는 작업만 순차 처리한다.
3. **TDD · 최소 테스트.** TDD 로 구현·검증하고, 완료 후엔 동작을 보장하는 **최소 테스트셋**만
   남긴다. 제거 대상은 change-detector 테스트 — 깨져도 버그가 아니라 리팩터·값 변경일 뿐인 테스트다.
   판별(litmus): "이 테스트가 깨지면 버그인가? → No 면 change-detector." `/pr` 이 이 기준으로 diff 를 스캔한다.
4. **worktree 격리.** 항상 origin/main 에서 worktree 새 브랜치로 시작한다. (`start` 가 강제)
5. **의도 인터뷰.** 구현 전 불명확한 의도를 인터뷰로 명확히 한다. (`start` 가 강제)
6. **실환경 e2e.** 마지막에 실환경 e2e(로컬 서버 + Chrome CDP)로 동작을 검증한다. (`show`)
7. **인간용 문서.** plan.md · PR 은 사람이 이해하기 위한 것 — 독립 작업별로 그룹화하고,
   as-is → to-be 로 설명하고, 이 작업을 안 한 사람도 이해할 만큼 평이하게 쓰고,
   UI/UX 변경은 캡처 이미지를 첨부한다.
8. **유지보수 설계.** 코드 구조는 사람의 이해를 위한 것 — 사람이 기능을 이해하는
   추상화 단위를 먼저 나누고, 모듈/클래스/파일이 그 단위와 **1:1 대응**하게 설계한다
   (이름만 보고 책임을 알 수 있게). 단순화 · SRP · 응집도↑/결합도↓ · SSOT ·
   적당한 수의 위계를 항상 고려하고, 기존 구조가 변경을 깔끔히 수용하지 못하면
   **선행 리팩토링(tidy-first)** 을 계획에 포함한다.
   (레퍼런스: <https://frontend-fundamentals.com/code-quality/code/>)

## 커뮤니케이션

사용자와의 설계·계획·리뷰는 **대화(채팅) 안에서 인라인**으로 한다.
내용을 별도 md 로 만들어 "열어보라"고 넘기지 않는다 —
파일(plan.md · PR desc)은 durable 기록/산출물로만 쓰고, 리뷰를 위해 파일 열람을 요구하지 않는다.

**한국어로 답한다.** 사용자 응답은 기본 한국어. (코드·식별자·고유명사는 원문 유지)

**평이하게 설명한다.** 의도 7 은 plan.md·PR 등 durable 문서에 적용되지만, 채팅 설명에도 같은 기준을 쓴다 —
핵심 결론을 먼저 말하고, 내부 용어·미정의 약어를 쓰지 않으며, 이 작업을 안 한 동료도 이해할 만큼 쉽게 쓴다.

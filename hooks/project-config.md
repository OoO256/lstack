# 프로젝트 검사 설정

검사를 도입하거나 적용 범위를 바꿀 때 읽는다. 프로젝트 root의 `.lstack.json`이
lint·구조 리뷰 확인을 켠다. 설정이 없으면 이 검사는 실행하지 않는다.

아래 주석은 필드별 작성 원칙이다. 실제 `.lstack.json`은 주석 없는 JSON으로 작성한다.

```jsonc
{
  // 현재 작업과 비교할 유효한 git ref. 프로젝트 기본 브랜치를 쓴다.
  "base": "origin/main",
  // git 상대 경로. 코드뿐 아니라 동작을 정하는 설정·프롬프트도 포함한다.
  "include": ["apps/**", "packages/**", "scripts/**", "agents/*.md", "skills/**", "hooks/**"],
  // 셸 문자열이 아닌 argv. 완료 검사와 CI는 프로젝트의 같은 lint 명령을 사용한다.
  // 기존 위반과 신규 위반을 구분하는 규칙·baseline은 이 명령이 소유한다.
  "lint": ["bun", "run", "lint:new"],
  // report: 구조 지적을 관찰·보고. enforce: 승인된 범위의 확정 blocker를 수정 후 재검토.
  // 둘 다 lint 실패와 실제 리뷰 누락·미완료·형식 오류는 통과시키지 않는다.
  "review": "report"
}
```

## 적용 범위와 실행 계약

네 필드를 모두 명시한다. 알 수 없는 필드, 잘못된 설정·base, git 충돌은 실행 오류다.
이미 검사 대상으로 등록된 설정을 삭제해도 통과로 처리하지 않는다.

`include`는 `*`(경로 한 부분), `**`(하위 경로), `?`를 지원한다. 개행 경로도 포함한다.
brace·문자 집합 glob, 절대 경로, 상위 경로는 받지 않는다. `.lstack.json` 자체는 항상
snapshot에 포함한다. 범위를 줄여 위반을 숨기지 말고 프로젝트 lint에서 점진 적용을 정의한다.

`lint`는 등록 worktree에서 실행하며 `LSTACK_BASE`로 base를 받는다. 종료 코드 0만 성공이다.
위반·실행 오류는 nonzero로 끝내야 한다. stdout의 단어로 성공을 추정하지 않는다.
실행 파일 누락·signal·120초 timeout은 실패다. lint가 코드를 바꾸면 현재 코드로 다시 검사한다.

## 점진 적용과 수정 권한

규칙 도입은 관찰 → 신규 위반 차단 → 기존 위반이 없는 영역 전체 차단 순으로 확대할 수 있다.
`review`는 구조 지적의 처리 방식이며, lint의 기존 부채 처리와는 별개다.
`report`의 의미적 지적은 한 번 메인에게 돌려 사용자에게 보고하게 한다.
`enforce`의 확정 blocker는 승인된 범위에서 고치고 새 리뷰를 받는다.

검사 범위가 서비스 코드를 포함해도 그 코드를 수정할 권한은 생기지 않는다.
검사 시스템 도입만 승인됐다면 기존 서비스 코드·제품 테스트는 정리하지 않는다.
검사 명령·범위 오류는 검사 시스템에서 고치고, 범위 밖 문제는 미해결로 보고한다.

실행 시점·명령·오류를 확인하려면 [lint·리뷰 확인](lint-and-review.md)을 읽는다.
